# WTT 页面移动端计算性能优化计划

## 背景（已探明的事实）

WTT 数据是全站大头：MS 类目 23,339 条比赛记录、297 个快照日期、约 1256 名球员（`wtt_data/ms/`，共 7.5 MB）。每次进页面全量重算，热点全部集中在共享引擎 `js/score-engine.js`：

1. **快照循环 O(S×N) 全量重放**（`calculateAllRankingsWithSeasonsAsync`，score-engine.js:420-474）：每个快照都对全量 log `filter` 出窗口（:426）+ `buildPlayerTypeBatches`（:427）+ 全量 forEach 重放（:428）。MS 下 ≈ 297 × 23k ≈ 700 万次记录遍历。
2. **批次索引是无效计算**：已验证 `getFreezeWeight`（score-engine.js:122）和 `getFormatMultiplier`（:55）在 `SCORE_TIME_DECAY_ENABLED === false`（WTT 模式，wtt_common.js:742 设置）时第一行就 return 1，`calcMatchPoints`（:140-143）走非衰减分支不用批次——即每个快照花大钱建的 `playerTypeBatches` 在 WTT 下**从未被消费**。
3. **实时排名每球员统计 O(P×L×2)**（score-engine.js:705-709 async、:615-618 sync）：对每名球员对全量 log filter 两次（总场次、胜率各一遍）。1256 × 23k × 2 ≈ 5800 万次比较。
4. **渲染层**：`wttRenderRankingTable`（wtt_ranking.js:384-426）一次渲染 1256+ 行 × 7 个 td，移动端还变成 grid 卡片布局（style.css:2248-2288）；每次排序/切节点/切语言全量重建。个人统计页搜索**无防抖**且每个按键把 `wttFuzzyMatch` 对全量球员跑两遍（wtt_personal_stats.js:337、:464-471）。

## 改动清单

### A. 计算层 — js/score-engine.js（结果完全不变）

**A1. 衰减关闭时跳过无效批次索引构建**
- score-engine.js:426-427（async）、:309-310（sync）、:671、:633、:366、:492 处的 `windowLog` filter + `buildPlayerTypeBatches(...)` 调用，用 `if (SCORE_TIME_DECAY_ENABLED !== false) { ... }` 守卫。
- 俱乐部模式（衰减开启）代码路径一行不动，零风险。

**A2. 实时排名每球员统计改单次遍历**
- score-engine.js:705-709（async）与 :615-618（sync）：先一次遍历窗口内记录，构建 `Map<player, {total, wins}>`，再在排序 map 中查表。语义与现有 filter 逐一等价（总场次 = 窗口内比赛记录数；胜率 = 胜场/总场，保留 `Math.round` 与 `'0%'` 边界）。保留现有 `sap.size === 0 || sap.has(n) || isProfileActivePlayer(n)` 过滤条件。

**A3. WTT 快照循环改单次增量重放（收益最大项）**
- 仅当 `SCORE_TIME_DECAY_ENABLED === false` 时启用新路径：每赛季按日期顺序**单次**遍历 sortedLog，累积积分；跨过每个快照日期时捕获 `{...sc}` 副本生成该快照排名，同时增量维护活跃球员 Set（替代每快照 O(L) 的 `getActivePlayers`）。复杂度 O(S×N) → O(N + S×P)。
- 正确性依据：现有逐快照重放是前缀一致的（每个快照都从赛季起始分重放到 sd，处理顺序相同），增量累积在每个时刻的 `sc` 与之完全相同。衰减开启（俱乐部）时保留现有逐快照路径不变。
- **验证**：写一个临时 node 脚本（不提交），加载 xd/md/ms 三个类目的真实数据，分别跑旧路径与新路径，对 `allRankings` 逐字段 diff，要求完全一致后删除脚本。

### B. 渲染层 — 低风险项

**B1. 个人统计页搜索防抖 + 单次匹配**（js/wtt_personal_stats.js:337）
- `input` 加 200ms 防抖（对齐全站全局搜索已有的 200ms 模式，js/common.js:561）；`doFilter()` 结果传给 `wttRenderPlayerIndex` 复用，消除每个按键的双份全量模糊匹配。

**B2. 排名表分页**（js/wtt_ranking.js:384-426）
- 排名表改为初始渲染前 200 行 + "显示更多"按钮，复用个人统计页已有的 `WTT_INDEX_PAGE_SIZE = 200` 分页模式（wtt_personal_stats.js:416）；排序、切换时间节点时重置到前 200 行。语言切换重渲也只重建当前已显示行数。

**B3. 排名表逐行开销削减**
- `wttGetPlayerAssoc` / `wttNameIdentity`（每行调用，含字符串处理与哈希）按球员名做 Map 缓存，本页生命周期内有效。

### C. CSS 减负（保守可选项，视觉有轻微变化，如不接受可去掉此项）

- 移动端媒体查询下移除球员卡片/大面积玻璃卡片的 `backdrop-filter: blur`（style.css:687 `.glass-card`，个人统计页 200 张卡 = 200 个合成层，是低性能 GPU 掉帧的典型来源）。
- 将高频 `transition: all` 收窄为具体属性。

## 明确不做

- 不引入 Web Worker、不做 localStorage/IndexedDB 数据缓存（改变新鲜度语义，留作后续可选项）。
- 同步版 `calculateAllRankingsWithSeasons`（:257-356）仅俱乐部小数据使用，不改其快照循环（A1/A2 中的守卫与统计优化除外）。
- 不动 `data/` 内容文件，无需跑 `sync_content.py`；不引入内联 onclick（遵守 AGENTS.md）；不改 nav/footer。

## 验证方式

1. A3 的 node parity 脚本：xd/md/ms 三类目旧 vs 新输出逐字段 diff 全等。
2. `python tools/ci_validate.py` 通过（确认数据约束未受影响）。
3. 本地起静态服务器，抽查 wtt_ranking / wtt_personal_stats / wtt_player：若干球员分数与优化前一致、进度条正常、排序/切节点/搜索/语言切换行为正常。

预计 MS 类目主线程计算量下降 60-80%（297×23k 的重放 + 5800 万次 filter 比较收敛到约 2 次全量遍历 + 每快照 O(P) 拷贝），移动端收益最明显；渲染层在实时节点下从 8800+ DOM 元素降到约 1400。
