# 阶段 4：让「实力是否增强」这句话本身可信

日期：2026-10-08
对象：`tools/_supervise.sh` / `tools/_finalize-12h.js` / `tools/bake-input.js`
起因：用户要求「续训 12h 的地狱 AI，增强其实力，做好防中断，若实力增强则烘焙」。

---

## 0. 一句话结论

上一轮 12h **确实把地狱档从实机 2.4% 打到了 11.7%**（已烘焙上线），但一路上有**六个
环节在无声地给假答案**：收尾只测一份候选、烘焙时把仿真胜率当成实机胜率写给玩家看、
守护的卡死检测算的是负数、杀不掉子进程留下孤儿、以及一条根本没接线的 `--from`。
本文逐条记下症状、修法，以及每条都是被什么证据逼出来的。

## 2. 六个被证伪的环节

### #15 收尾只测一份候选，而「仿真最佳」根本不等于「实机最佳」

`_finalize-12h.js` 原来只跑 `index.json` 的 `best.file`。问题在于仿真/实机在地狱档
**会大幅分叉且方向不定**：

| 权重 | 仿真地狱 | 实机地狱 | Δ |
|---|---|---|---|
| `input3-12h` ckpt-008500 | 16.0% | 11.7% | −4.4pp |
| `input3-gs` best@ep2000 | 18.8% | **2.3%** | **−16.5pp** |

`input3-gs` 那一轮的最佳权重落在 **ep 2000**（一万两千局里的头一截），后面十几份检查点
一份都没被看过——候选集被压成了 1，而那 1 份是按仿真分挑的。

**修法**：新增 `--topN N`（默认 3）。按仿真三档加权分取前 N 份，**逐份跑实机管线**，
最后按**实机**加权分挑，而不是按仿真分挑。代价是每份候选约 10 分钟实机对局。

### #16 烘焙把仿真胜率写进了给玩家看的 meta

```js
const evHell = wr['hell'] || cand.live['hell'] || 0;   // ← wr 是仿真值
```

`INPUT_AI_META.evalHell` 是页面上**玩家唯一能看到**的胜率数字。原来取的是仿真值，
于是线上那份权重的 meta 写着 `evalHell: 0.75`，而它在游戏里被地狱 AI 打成 **2.4%**。
阶段 3 的全部结论就是「仿真数字不能当实机数字用」，而 meta 恰恰是最该守住的地方。

**修法**：`evalHell`/`evalDefault` 改写实机实测值；仿真值另存 `simEval`，
实机逐档结果存 `ladderLive`（含时间、种子、局数）。两边都留痕，以后一眼能看出又岔开了。

### #17 收尾的基线描述的是一份**已经不在线上**的权重

`tools/logs/baseline-live.json` 的 note 写着「游戏当前加载的那份权重」，
实际记录的还是 v3/ckpt-003600。已按当前线上权重（12h/ckpt-008500）重建，
旧的归档到 `baseline-live.v3-archive.json`。

### #18 守护的卡死检测算出来的是负数

第一版用 `date +%s - stat mtime` 算静默时长，`IDX_AGE` 实测 **−1791388291**：
`stat` 给的是 epoch 秒，`$SECONDS` 是本进程运行秒数，两者不是一个量纲，
相减得到负数，判定恒不成立，卡死检测形同虚设。

改掉之后又暴露第二层：**这台机器的墙上时钟在一次会话里往前跳了 41 小时**
（`date` 从 10-06 07:00 变成 10-07 23:51，`index.json` 里的 `updated` 字段比它的
mtime 早整整 24 小时）。任何基于墙钟差的判据都会随时失真。

**修法**：改成**按内容**判定——轮询 `index.json` 里的 `elapsedSec`，数它连续多少次
轮询没变。训练器每落一次检查点必然重写它并让该值递增，所以「没变」就是「没在推进」。
对时钟跳变完全免疫。

### #19 Git Bash 杀不掉原生 node 子进程 → 孤儿训练器

守护里 `kill -TERM $CHILD` 之后，MSYS 认为子进程已退出、继续重启，
**Windows 侧的 node 却还在跑**（冒烟测试 smoke2 留下两个孤儿，全程零报错）。

后果就是 2026-10-05 21:12 那次事故的机制：锁一释放，第二个守护再起一个训练器，
两个进程并发写同一份 `index.json`，断点损坏。

**修法**：三级降级停机（`stop_child`）——
1. 哨兵文件（训练器自己的通道，Windows 上唯一可靠，且不丢进度）；
2. `SIGTERM`（次优，MSYS 投递不可靠）；
3. `taskkill /F /T /PID <Windows PID>`，按 `--run-name <RUN>` 匹配出本 run 的进程，硬杀。

另加 EXIT trap：守护自己被杀时**先停掉训练器再放锁**，杜绝孤儿。

### #20 「叫停」这个动作在最需要它的场景失效

轮询里原本只把停止请求转成哨兵，然后干等。训练器启动段（基线标定 + 500 局预填回放）
不查哨兵，真卡死更是永远等不到——也就是**训练已经不正常时，叫停反而不管用**。

**修法**：`STOP_USER_GRACE`（默认 300s）宽限后自动转入 `stop_child` 的三级降级。

### #21 「取前 3 份候选」取到的其实是同一份权重跑了 3 遍

上一条 #15 的修法（`--topN` 多候选实机择优）本轮**没有生效**，而且失效方式很隐蔽：
`_finalize-12h.js` 按 `c.file`（文件名）去重，而 `train-input3.js` 的 `writeCheckpoint`
落盘的是 **`bestNet`**（当轮选优分最高那份权重），**不是该 ep 当时的策略**。于是只要
没有新的「★新最佳」，后面落的所有检查点都是同一份权重的副本。

实测（2026-10-08 07:0x，本轮跑到 ep 5200 时）：

```
17 个 ckpt-*.json  →  md5 全部等于 34a0f85cb92852eb7b766a85c4863a6f
```

`bestNet` 最后一次更新在 ep 3500（此前只有 ep 500、3500 两次「★新最佳」），
之后 1700 局全在复制粘贴同一份 10MB 文件 —— 166MB 磁盘里只有 1 份有效权重。

后果：收尾会拿这**同一份权重跑 3 次实机管线**（每份约 10 分钟，白烧 30 分钟），
而且报告里会打印 3 行几乎一样的「实机加权分排名」，看上去像做了多候选筛选，
实际一份备选都没有。#15 想根治的「仿真最佳 ≠ 实机最佳，所以要多试几份」被架空了：
**候选集里根本没有第二个可试的东西。**

**修法**：`_finalize-12h.js` 的 `candidateFiles()` 改按**文件内容 sha1** 去重
（同名不同内容保留、同内容不同名折叠），并在报告里如实写明
`distinctWrites` / `dupCheckpoints`，控制台直接说破「要求 3 份，实际只有 1 份」。
去重后再 `slice(0, topN)` —— 先去重后截断，顺序不能反。

**注意**：这修的是「收尾别自欺」，**没有**让候选集真的变多样。训练器仍然只存
bestNet，所以一轮跑完通常就只有 1 份候选。要真正拿到多份可选项，得让训练器
额外落一份「当轮策略」（比如每 N 局存一次 `cur-*.json`），那是改 `train-input3.js`
的事，本轮没动（改了会让这一轮的归因失效）。

## 3. 本轮训练的设计（只动一个变量）

上一轮课程 `hell:0.25,elite:0.30,extreme:0.25,extreme-max:0.20` 把地狱排在**最前**，
之后 7500 局全打别的档。曲线证实这是灾难：ep 250 地狱 9.1% → ep 2500 地狱 4.3%
（地狱段自己都没训上去）。**2500 局纯地狱训练换来 0 提升，不是"不够久"，是排错了位置。**

本轮 `_launch-hell12h.sh`：

```
default:0.10 → extreme-max:0.15 → grandslam:0.25 → hell:0.50   （--end hell）
```

* 地狱放**最后**且占一半预算——排后面才不会被后面的阶段覆盖掉。
* `grandslam` 25%：它是**实机真实可选**对手，收尾闸门给它 0.45 权重。
  `elite/extreme/extreme-max` 游戏里选不到，不单独占预算。
* 其余超参与上一轮**逐字相同**，只动「课程与顶档」一个变量，结果才可归因。

## 4. 遗留的判断

**已验证并推翻（2026-10-10）**：BC「追球监督」保鲜池的样本全部来自
`naiveCmd = { tx: ball.x, my: 0.5 }`——曾怀疑**深度旋钮恒为中位**导致「够不到球」。
实测（`tools/_diag_depth.js`，20 局实机、逐决策步统计）**证伪**：

| 权重 | my 均值 | my 众数 | 偏前(<0.5) | tx 均值 |
|---|---|---|---|---|
| input3-hell12h/ckpt-007000 | 0.427 | 0.462（83.6%） | 94.6% | 0.118 |
| input3-12h/ckpt-008500（线上基线） | 0.529 | 0.462（80.8%） | 83.1% | 0.126 |

深度**没有**锁在中位，反而 80%+ 挤在 my=0.462 且大幅偏前。真正一样的是
**tx 均值 ≈ 0.12**（横向几乎不动，中位是 0）——两份权重横向都不跟球。
所以「够不到」不是深度问题，是**横向追踪**问题。§4 这条猜测到此作废，
不要再按「调深度旋钮 / 降 bcmix」的方向去试。

## 4b. 这一轮为什么必然没达标（2026-10-10 复盘）

12h 跑完，闸门 B 判负（实机 vs 地狱 2.6% vs 基线 11.7%，−9.1pp），未烘焙，
`js/input-weights.js` 保持原样（md5 未变）——**这是正确的安全结果**。
但真正的原因不是运气差，是三个可查的事实：

### (1) ~~`--eval 77` 没生效在训练期~~ —— **这条也是错的，已撤回**

曲线里 ep≤4500 的胜率全是 12.5 的整数倍 → 那些点每档只打了 12 局，一度以为
`--eval 77` 没作用在训练期评估上。**实际是重启历史造成的**：本轮守护重启过 3 次，
前 3 次启动用的仍是旧的 `--eval 20`（日志里三次「每轮验证：4 档 × 20 局」），
第 4 次（10-08 06:20）才切成 77。曲线是**跨多次运行追加**的，所以前半段留着旧口径的点。
`--eval` 本身工作正常：ep4750 之后的 13 个点全是 77 局，断点 `cfg.eval=77`。

**但结论方向仍然成立，只是理由要换**：77 局/档在地狱档（p≈0.1）标准误约 ±3.4pp，
而 ep 7250~8250 的地狱读数是 11.0 / 20.1 / 9.1 / 14.9 —— 彼此的差都在噪声内，
**读不出趋势**。而且这 13 个 77 局点里只有 7 个落在 hell 段。真正的问题是
**有效样本量 × 有效训练量都不够**，不是参数没传对。

另一条独立且成立的事实：这轮地狱段只拿到 **2300 局**（ep 6000~8300），
是 50% 预算段的 38%——`--eval 77` 让每轮验证从 ~160s 涨到 ~630s，
验证开销吃掉了本该给训练的时间。

### (2) ~~选优分把「地狱」和「本档」双计~~ —— **这条是错的，已撤回**

曾以为 `--end hell` + hell 段 `phase.tag='hell'` 会让地狱被双计成
0.45+0.30=0.75、default 只剩 0.25，因而「训练按 default 选、验收按地狱判」。
**这是个数学错误**：当两项是同一个数时，`0.45t + 0.30t + 0.25d` 与
`0.75t + 0.25d` **完全相等**（已用四组真实数值验证，差恒为 0）。
双计与否不改变分数，所以权重分配**本来就是** 0.75 地狱 / 0.25 default，
配置没有错。（我一度为此改了 `train-input3.js`，验证后确认是空操作，已 `git checkout` 还原。）

真正该问的是：这轮的地狱只训了 **2300 局**（ep 6000~8300，占 50% 预算段的 38%），
而选优分要在这种样本量上分辨 1.3% vs 20.1% 的差异——见 (1)。

### (3) 早停护栏被噪声牵着走，又恰好没兜住

`keep = (sc > bestScore) && (epD >= bestDef - 0.05)`：default 护栏是相对**上一个
best** 的 -5pp 浮动窗口。12 局评估下 epD 本身就能跳 ±50pp，于是「最佳」几乎随机，
ep 3500 之后再没变过（选优分冻结 42.5）。ABORT 早停（连续 4 块退化）在 ep 2250
误触发过一次（12 局噪声），把一个正在推进的进程停了。

**结论**：这一轮不是「时间不够」，是**评估样本量与训练量都不足以支撑结论**。
下一轮若不先修这几件事，再跑 12h 还是同一个结果。优先级：
① 训练期验证局数真的提上去（确认 `--eval` 作用在训练期那一处），并把地狱段
   预算占比往上提（这轮只拿到计划量的 38%）；
② 早停护栏改成对 best 的绝对地板，别用 -5pp 浮动窗口；
③ 横向追踪（tx 均值 0.12）才是「够不到」的真正抓手，值得作为下一轮的主假设去试。

**方法论**：本轮所有修复都先用替身（`_stub-trainer.js`）跑过冒烟测试才敢上真活，
其中卡死检测的负数 bug、杀不掉子进程、锁自愈三条都是测试逼出来的，不是看代码看出来的。
