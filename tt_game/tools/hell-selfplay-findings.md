> 训练器 `tools/train-hell.js`（遗传算法），目标策略 `js/learned-policy.js` 的 `LEARNED_POLICY`（42 维）。
> 五轮均在 `--no-write` 下跑，**从未自动覆盖 `js/learned-policy.js`**，候选一律交人确认。
> 与第 1–5 轮训的「玩家侧 DQN」（`js/input-agent.js` / `js/input-weights.js`）**完全无关**。

|---|---|---|---|---|

| 第 3 轮 | 方案 A，`--from` 第 2 轮候选 | 330 | **53.08 %**（独立复评 3200 局双向实机口径） | **否（退步 4.2 pp）** |

**第 1、2 轮都真的变强了。** 第 1 轮被「对手口径错误」误判掉；第 2 轮换用正确的主目标口径后提升更明显（+7 pp 级别）。

**第 3 轮是一次失败，且失败方式很有教育意义**：它对第 2 轮候选的胜率是 **60.39 %**（3200 局双向，真实提升，不是噪声），可对**线上地狱反而从 57.27 % 掉到 53.08 %**。三者构成完整的石头剪刀布：

```
第 2 轮候选  ──57.27 %──▶  线上地狱
第 3 轮候选  ──53.08 %──▶  线上地狱
第 3 轮候选  ──60.39 %──▶  第 2 轮候选
```

⇒ **适应度里的「现役」参照一旦换成上一轮的候选，GA 就会朝着特化那个候选的方向漂移，
在自对弈曲线上看着一路涨，对真实目标的胜率反而倒退。** 详见第 10 节。

**第 4 轮是决定性的一轮：把「对手太弱」这个根因解决了。** 先量化（`tools/_opp-ladder-hell.js`，每个对手 1800 局双向）：

| 对手 | 第 2 轮地狱的无偏分点率 | 判读 |
|---|---|---|
| default 默认 AI | 85.50 % | 饱和，零梯度 |
| pusher 搓球狂（worker 里 10 行手写常量） | 85.14 % | 饱和，零梯度 |
| pb 加强玩家模型 | 91.17 % | **最弱**，饱和 |
| grandslam 大满贯预备种子 | 85.53 % | **并不比 default 强**，加它没用 |
| **nemesis 地狱 AI 克星** | **38.20 %** | ← **仓库里唯一的强对手** |

⇒ 原适应度四个对手**全部挤在 85–91 % 的饱和区**，0.48 的权重提供不了梯度；而唯一有真实压力的
`nemesis`（`js/learned-policy-nemesis.js`，GA 专门针对地狱训出来的克制策略）**根本没进适应度**。
方案 B 把 `nemesis`（0.30）与归档旧线上（0.22）一起钉进池子，`pusher`/`default` 降权/剔除。
结果：vs 克星 **38.20 % → 53.77 %（+15.6 pp）**，vs 现役 **+9.8 pp**，而四个**留出对手**
（`default` / `pusher` / `pb` / `grandslam`，均不在池内）全部在 ~1 SE 内无塌陷 ⇒ **真泛化，非拟合**。详见第 12 节。

## 1. 地狱 AI 是什么

- `js/learned-policy.js` 导出 `LEARNED_POLICY`（partial，未设字段回落 `POLICY_DEFAULT`）+ `LEARNED_META`。
- 实机经 `js/policy.js#strongVec()` 合并：
  ```js
  const L = Object.assign({}, LEARNED_POLICY, { moveSpeed: 2.8, moveErr: 0.03, moveZ: 2.6 });
  ```
  ⇒ **idx 0/1/2（`moveSpeed`/`moveErr`/`moveZ`）在实机被硬写**，`LEARNED_POLICY` 里的原始值永远不用。
- `policyForModel('hell') = unflattenPolicy(strongVec())`；`grandSlamPolicy()` 另硬写 2.9/0.02/2.7。

## 2. 训练器 `tools/train-hell.js`

- GA：`pop 24`；每代每个体对 4 个对手（`default` 默认 / `pb` 加强玩家模型 / `pusher` 搓球 / `self` 自对弈）各 2 种子；
- 每 10 代落盘 `tools/train-hell-curve.json` + `tools/train-hell-best.json`；收尾写 `tools/train-hell-candidate.json`；
- `--from <file>` 读 `{vec:[...]}` 续训；`--no-write` 永不覆盖 `js/learned-policy.js`；
- 内置最终验证 = 4 种子 × 40 局（新 vs 默认 / 新 vs 加强玩家模型 / **新 vs 旧地狱头对头**）。

## 3. 第 1 轮（850 代，旧适应度）为什么「看起来」零提升

旧适应度：`fit = 0.34*vs加强玩家 + 0.26*vs默认 + 0.26*vs自对弈 + 0.14*vs搓球`。

三条根因：

1. **适应度没有梯度**：`vs加强玩家 + vs默认` 共 60 % 权重常年顶在天花板（0.94 / 0.90），几乎贡献 0 梯度；唯一能动的自对弈项只占 0.26，且对手是**每代在动的 `best.v`（移动靶）**。
2. **★ 三维在实机里是死的**：训练/验证走 `unflattenPolicy(rawVec)`，实机走 `strongVec()` 硬写 idx 0/1/2 ⇒ 这三维练了也白练。第 1 轮候选**最大的改动恰好是 `moveZ`**（0.984→1.796）。
3. **跨代选优有噪声**：每代种子 `BASE.x + g*991`（跨代不可比），一代只跑 2 种子 × 24 局 ≈ 48 局（SE ≈ 7 pp）。

第 1 轮实测：`best.fit` 0.8087 → 0.8256 @ gen 524，之后 325 代无突破；内置验证 vs 旧地狱 49.36 %。

## 4. 方案 A 的四处改动（全部在 `tools/train-hell.js`）

1. **适应度主目标反转**：`fit = 0.52*vs现役 + 0.20*vs加强玩家 + 0.16*vs默认 + 0.12*vs搓球`。
2. **对手固定为 `curVec`**（不再用每代移动的 `best.v`）——这才是真正的「vs 现役头对头」。
3. **冻结 idx 0/1/2**：`FROZEN = [[0,2.8],[1,0.03],[2,2.6]]` + `applyFrozen()`；`mutate()` 跳过、种群随机初始化 `applyFrozen()`、续训起点也 `applyFrozen()` ⇒ **训练向量 == 实机向量**。
4. **每代局数 24 → 60** + **跨代固定种子**（去掉 `+g*991`），降低选优噪声。

## 6. ★ 口径修正：`tools/_hell-h2h.js`

`_hell-h2h.js` 原来拿 `unflattenPolicy(flattenPolicy(LEARNED_POLICY))`（**原始向量**）当对手 —— 那是**游戏里不存在的地狱 AI**（实机走 `strongVec()`）。
第 1 轮「49.9 % 持平」的结论就是被这个口径毁掉的（其最大改动恰是实机被覆写的 `moveZ`）。

已修正为默认 `P.strongVec()`（实机口径），`--opp-raw` 可回退；并新增 `--from <file>` 指定候选来源。校验：

```bash
node tt_game/tools/_hell-h2h.js 150 6                      # 默认实机口径
node tt_game/tools/_hell-h2h.js 150 6 --opp-raw            # 原始口径对照
node tt_game/tools/_hell-h2h.js 200 8 --from <candidate.json>
```

用实机口径重测第 1 轮候选（1800 局双向）：**52.22 %**（不是 49.9 %）。⇒ 第 1 轮也不是白跑。
用实机口径复评第 2 轮候选（3200 局双向）：**57.27 %**；同一候选的原始口径只有 48.32 %。
**同一份权重，换个对手口径就从「更强」变成「更弱」** —— 这是本轮最值得记住的一件事。

> **注意**：`train-hell.js` 内置的最终验证本身就是对的 —— 它的 `curVec` 已 `applyFrozen`。

## 10. 第 3 轮（2026-10-17 19:46:23 → 10-18 01:28:15）——共演化循环，实证失败

### 配置

起点 = **第 2 轮候选**（用户指令「续训」），其余与方案 A 完全一致（330 代 / 60 局每代 / 20 workers / 冻结 idx 0,1,2 / 跨代固定种子）。

守护链路：`_supervise-hell.sh 330 --workers 20 --no-write`，20512 s，**0 次重启**，正常收工。

### 训练器自己看到的

```
fitness 0.7485 @ gen 318   （第 2 轮起点 0.6723，第 2 轮收官 0.7370）
vsDefault  86.47 %（参照 84.71 %）    vsPlayer 90.32 %（参照 91.37 %）
vs旧地狱   60.80 %（参照=第 2 轮候选；内置验证只 160 局，SE≈3.9 pp）
```

内部曲线尾段 `vsCur` 稳定 59–62 %，护栏 `vsPB` 91 % / `vsDef` 86 % / `vsPush` 85 % 与第 2 轮持平。**看起来是一次干净的成功。**

### 独立复评（`tools/_hell-h2h.js`，每项 3200 局双向）

| 对局 | 结果 |
|---|---|
| 第 3 轮候选 **vs 线上地狱**（实机口径） | **53.08 %**（候选先手 52.97 / 参照先手 46.81） |
| 第 3 轮候选 **vs 第 2 轮候选** | **60.39 %**（候选先手 60.43 / 参照先手 39.65） |

SE 均 ≈ 0.9 pp ⇒ 两个数字都远在噪声之外。

### 结论

对上一轮候选的 +60.39 % 是**真实的**，不是自娱自乐的噪声；但它对**真正的目标（线上地狱）退步了 4.2 pp**。三者的关系是非传递的：

```
A = 第 2 轮候选   B = 第 3 轮候选   S = 线上地狱
A > S  (+7.27 pp)
B > A  (+10.39 pp)   ← 第 3 轮优化的正是这一条
B > S  (+3.08 pp)    ← 但仍不如 A
```

**根因**：`train-hell.js` 里「现役」这个参照就是 `--from` 给的起点，适应度的 0.52 权重全部压在上面。第 2 轮的起点是**线上地狱**（固定），所以第 2 轮优化的是真目标；第 3 轮的起点换成了第 2 轮候选（也是固定，但已经是被特化过的产物），GA 于是把 52 % 的适应度预算拿去「专治第 2 轮」，牺牲了对 S 的通用强度。护栏权重没变也没能救回来——因为护栏参照（默认/加强玩家/搓球）从来不是被特化的那个。

### 下一步的三个协议选项

| | 做法 | 评价 |
|---|---|---|
| **A** | 参照固定回**线上地狱**（第 2 轮的做法），多花算力 | 唯一产出真实提升的一轮；涨得慢但每一分都算数 |
| **B** | 参照用**轮换集合** {线上, 第 2 轮候选}，`vs现役` 取均值 | 打破循环，同时保住第 2 轮已得的 +7 pp |
| **C** | `vs现役` 权重 0.52 → ~0.35，权重还给护栏 | 最保守，慢但不易特化 |

无论选哪个，**判定标准永远是「候选 vs 线上地狱（`_hell-h2h.js` 默认口径）」的 3200 局双向结果**，
内部 `vsCur` / `fitness` 一律不作为采纳依据。

## 12. 第 4 轮：方案 B（对手池化）— 2026-10-19 01:20:04 → 04:28:22

### 14.3 ★ 踩到的两个真 bug（都写进了 `tools/_adopt-hell.js` 的注释）

**坑 1：`P.strongVec()` 返回的是 42 维「向量数组」，不是「策略对象」。**
最初写 `P.flattenPolicy(P.strongVec())` 去做「逐位比对」——`flattenPolicy` 按 42 条路径去
策略对象上取值，对一个数组取不到任何一条，于是**全部静默回落 `POLICY_DEFAULTS`**。
后果有两层：① 逐位比对看起来「42 维全错」，排查成本极高；② **归档文件悄悄存成了默认值**，
不是被替换策略的真向量 —— 这个错误如果没被发现，下一轮的参照池就会拿一坨默认值当对手。
正确写法：`P.strongVec()` 直接就是 42 维 vec 数组，和 `cand.vec` 逐位比即可。

**坑 2：只清 `require.cache` 不够，`global.LEARNED_POLICY` 还在。**
`js/policy.js` 第 19–30 行在 require 时把 `LEARNED_POLICY` 挂到 `global`，
于是 `typeof LEARNED_POLICY === 'undefined'` 判 false ⇒ 重写文件后再 require
**不会重新读文件**，校验比的是旧值。正确做法：`delete global.LEARNED_POLICY;` 之后再 require，
且**必须在全新进程里做**（同进程内 `require` 缓存已固化）。

> 这两条合起来说明：**凡是「改完文件后验证改动生效」的脚本，都要用全新进程 + 显式清 global。**

### 口径说明（重要，容易看错）

`tools/_hell-h2h.js` 的「候选」默认读的是 **`tools/train-hell-candidate.json` 这个文件**，
不是线上 `js/learned-policy.js`。两者之间靠一条**逐位相等**的链连接：

```
js/learned-policy.js  --(全新进程 require)-->  P.strongVec()  ==  _r5-candidate.json 的 vec
                                                     mismatches = 0
```

而 `P.strongVec()` 正是游戏里地狱 AI 真正使用的策略（`policyForModel('hell')` 走它）。
⇒ 候选文件被测出的强度，就是线上策略的强度。

为把这条链再钉死，另外做了一次**直接测线上向量**的复核：
把 `P.strongVec()` 导出成 `tools/logs/_live-vec-check.json`，再用
`node tools/_hell-h2h.js 200 8 --from tools/logs/_live-vec-check.json --versus tools/logs/_shipped-20261018-r2-ingame.json`
直接对 R2 打 3200 局，结果见 `tools/logs/_h2h-adopt-live-vs-r2.txt`。

### 为什么这条链必须用「全新进程」

`js/policy.js` 第 19–30 行在 require 时把 `LEARNED_POLICY` 挂到 `global`。
只清 `require.cache` 再 require，拿到的仍是**旧值** —— 于是逐位校验会「通过」，
但比的是被覆盖之前的东西。必须 `delete global.LEARNED_POLICY;` 后重新 require，
或干脆开一个全新进程（`node -e` 天然是全新进程）。
